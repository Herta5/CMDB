# CMDB 产品文档补全设计

## 背景

CMDB 已具备身份、业务项目、云接入源、资源同步、资产生命周期、审计和控制台页面，但 `docs/project/` 下的五份规范目前只记录了少量业务红线。根目录 `README.md` 包含较多实现细节，却不能替代稳定的产品定义，也没有清楚区分目标能力与当前交付状态。

本次工作补全产品文档，不修改业务代码。完成后的文档必须既能指导后续研发与验收，又不能把尚未实现的目标能力描述成当前事实。

## 已确认的产品口径

- 控制台使用统一的“云同步管理”入口管理阿里云和 AWS 接入源；两家云平台采集器仍是边界清晰的独立模块。
- 资源列表必须支持排序、分页和列配置。这些是目标产品要求；当前实现不足应记录为交付差距。
- 系统管理员是最高权限角色，可以跨项目查看和管理数据，无需预先加入项目。
- 普通用户仍以业务项目作为最高级的数据归属和权限隔离边界，并依据项目角色获得权限。
- 既有资源身份、凭证保护、同步失败保护和资源删除确认规则保持不变。

## 文档目标

补全后的文档应满足以下使用场景：

1. 产品和研发人员可以快速确认首期范围、明确不在范围内的能力及术语含义。
2. 后端和前端研发可以从同一份角色权限、领域状态和同步流程定义开展实现。
3. 测试人员可以按端到端场景验证数据隔离、资源同步、资产生命周期和敏感信息保护。
4. 项目维护者可以判断某项能力是产品要求、当前已实现能力，还是后续待补差距。
5. 新需求与现有规范冲突时，可以定位唯一的权威文档，而不是从代码或 README 推断产品决策。

## 文档信息架构

作为项目规范入口，说明文档的适用对象、权威关系、推荐阅读顺序和各文件职责。该文件只做导航，不复制具体业务规则。

### `docs/project/overview.md`

保留产品定位和首期范围，并补充：

- 产品目标、目标用户和核心价值；
- 系统管理员、项目管理员、项目成员三类角色概览；
- 从建用户、建项目、接入云账号到查看资产和审计的核心业务闭环；
- 首期纳入与明确不纳入范围；
- 公共核心与阿里云、AWS 平台模块的职责边界；
- 关键术语及范围变更规则。

### `docs/project/domain-model.md`

补充用户、业务项目、成员关系、接入源、同步任务、三类资产、访问端点和审计日志的关系及约束，并明确：

- 对外身份与内部主键的边界；
- 项目编码、负责人、项目状态和成员角色语义；
- 接入源与项目、资源的单向归属关系；
- 三类资产的公共字段与专属字段；
- 云端状态和 CMDB 资产状态是两个不同维度；
- 原始属性、易变观测属性、访问端点和时间字段的维护责任；
- 级联删除与长期保留审计的边界。

### `docs/project/resource-sync.md`

把同步规范扩展为可实现、可验收的流程定义，包括：

- 接入源配置、启停、连接测试、自动与手工触发；
- 排队、运行、成功、部分成功和失败任务状态；
- 同源互斥与异源并行；
- 类型级采集隔离、统计口径和失败保护；
- 新增、更新、未变化、失联、恢复和物理删除判定；
- 失败或部分成功任务的重试关系；
- 服务重启后的排队任务恢复和异常中断任务收敛；
- 任务错误摘要及审计的敏感信息边界。

### `docs/project/security.md`

补充身份认证、授权矩阵、凭证、审计和错误披露要求，包括：

- 系统管理员作为明确的全局最高权限例外；
- 项目管理员和项目成员的项目内权限；
- 登录失败防枚举、停用账号立即失效、JWT 最小声明；
- 用户、项目、接入源、资源、同步任务和审计接口的角色矩阵；
- 凭证加密、替换、脱敏展示及密钥管理边界；
- 审计动作、操作人快照、筛选、稳定分页和删除后保留；
- 未授权项目与不存在项目使用一致响应的防枚举要求。

### `docs/project/frontend-guidelines.md`

把视觉原则扩展为页面级产品体验规范，包括：

- 左侧分组导航、顶部项目切换和统一“云同步管理”入口；
- 登录、资产列表、项目管理、用户管理、云同步管理和审计日志页面职责；
- 系统管理员“所有项目”上下文与普通用户项目上下文；
- 列表筛选、排序、分页、列配置和状态持久化要求；
- 加载、空数据、失败、无权限、提交中和危险操作确认；
- 失联资产、同步状态和敏感凭证的展示规则；
- 桌面、平板、键盘可达性和中文文案要求。

### `docs/project/acceptance.md`

集中记录跨领域验收场景，避免在各规范中重复完整流程。场景按“前置条件—操作—预期结果”组织，覆盖：

- 首次管理员初始化与登录；
- 用户和项目权限管理；
- 跨项目访问隔离与系统管理员全局权限；
- 两个平台接入源管理及连接测试；
- 自动同步、手工同步、并发拒绝、部分成功和重试；
- 资源幂等更新、失联、恢复和 24 小时后删除；
- 资源列表查询能力及页面状态；
- 凭证、用户内部 ID 和云端错误的防泄露；
- 审计查询与被删除对象的历史可追溯性。

### `docs/project/implementation-status.md`

以提交 `8c88e59` 为初始核对基线，逐项标记：

- **已实现**：代码、页面或测试已提供完整行为；
- **部分实现**：已具备主流程，但尚未满足全部产品要求；
- **待实现**：规范要求存在，当前仓库没有对应能力。

状态表必须提供代码或测试位置作为核对依据，并明确它是可更新的交付快照，不得覆盖其他文件中的规范要求。当前已知的主要差距是资源列表排序、完整分页交互和列配置。

### 根目录 `README.md`

保留部署、开发和 API 快速说明，只新增项目产品文档入口及“README 不替代项目规范”的提示，不复制详细产品规则。

## 内容边界与表达规则

- `docs/project/` 中除 `implementation-status.md` 外均描述应长期遵守的产品要求。
- `implementation-status.md` 只描述特定提交的实现事实，并以证据路径支撑结论。
- 使用“必须”“不得”表达强制要求，使用“支持”“提供”表达产品能力，避免“建议”“尽量”等无法验收的措辞。
- 所有用户可见角色、状态、动作和错误语义使用中文；代码值在首次出现时以反引号附注。
- 不新增未获确认的云平台、资源类型、微服务、移动端适配、手工编辑云属性或新的角色类型。
- 不在产品规范中复制完整 REST API 清单、数据库表结构或部署命令；这些内容继续由 README 和代码负责。
- 跨文档规则只在一个主责文件中完整定义，其他文件通过相对链接引用。

## 事实核对方法

文档编写以以下顺序取证：

1. 用户本次确认的产品口径和根目录 `AGENTS.md` 的业务红线；
2. `docs/project/` 中不存在冲突的现有规范；
3. 后端路由、领域服务、数据库约束和自动测试；
4. 前端路由、页面、状态管理和自动测试；
5. 根目录 README 中的部署与接口说明。

代码事实只能用于填写实现状态或细化既有产品规则，不能自行扩大产品范围。

## 验证方案

文档完成后执行以下检查：

1. 搜索未决标记、占位符和旧产品名称，确保没有遗漏的待补内容。
2. 检查所有相对链接可以解析，文档索引覆盖全部项目规范。
3. 对照三项已确认口径，确保导航、列表能力和系统管理员权限无矛盾表述。
4. 对照 AGENTS.md 的业务红线，检查项目归属、资源身份、失败保护、删除条件和敏感信息要求均有明确落点。
5. 对照后端路由、前端路由及测试清单，确认实现状态表的证据和状态准确。
6. 运行 Markdown 结构检查脚本，验证标题层级、重复标题和本地链接。
7. 因仅修改 Markdown，不要求重新运行与代码行为无关的全量测试；但交付时保留修改前基线测试结果，并确认仓库未出现非文档改动。

## 交付与版本控制

- 所有修改在 `codex/product-docs` 分支的隔离工作区完成。
- 设计说明、产品文档补全和必要的校验修正分别形成可验证提交。
- 完成后将工作分支纳入最新 `main`，复核文档和工作区状态，再以本地合并或 Pull Request 合入 `main`。
